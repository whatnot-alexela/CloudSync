# YandexDL Desktop — прототип (PySide6 + CDP)

Один процесс, одно окно вместо «два терминала + mitmproxy + системный прокси + сертификат».
Окно — обычный браузер со вкладками: вкладка 0 закреплена за нашим сайтом (galerея/статус
server.py, без крестика), остальные вкладки — нормальный браузер (адресная строка,
назад/вперёд, "+ вкладка", закрытие крестиком), по умолчанию вторая вкладка открыта на
disk.yandex.ru. Можно открыть Диск сразу в нескольких вкладках — захват следит за всеми.

```
┌───────────────────────────── MainWindow ─────────────────────────────┐
│ [◀][▶][⟳] [ адресная строка ] [+ вкладка] [Лог]                       │
├───────────┬───────────────────┬───────────────────────────────────────┤
│ YandexDL  │ Яндекс Диск       │ (ещё вкладки — обычный браузер)        │
│ (закреп.) │ disk.yandex.ru    │                                        │
│ = /status │ пользователь сам  │                                        │
│  сервера  │ логинится, листает│                                        │
│           │ ленту «Фото»      │                                        │
└───────────┴───────────────────┴───────────────────────────────────────┘
          │                              │
          │ Flask в потоке процесса      │ CDP: следит за КАЖДОЙ вкладкой
          ▼                              │ с disk.yandex в URL
   server/server.py (не менялся)         ▼
   /api/ingest, /api/auth  ◄──── app/capture_cdp.py (замена addon.py)
```

Лог перехвата и счётчики (кластеры/ресурсы/сколько вкладок под наблюдением) — в
выезжающей снизу панели, открывается кнопкой «Лог» на тулбаре, чтобы не загромождать
«браузерность» основного окна.

**Что изменилось по сравнению с оригинальным YandexDL:**

- `capture/addon.py` (mitmproxy-аддон) → `app/capture_cdp.py`: та же логика извлечения
  данных (clusters/resources, sk, connection_id, Cookie/Set-Cookie), но источник — не
  перехват HTTP-прокси, а события `Network.*` от Chrome DevTools Protocol, которые отдаёт
  сам встроенный в приложение Chromium (QWebEngineView). Прокси и сертификат не нужны.
- `server/server.py` сохраняет совместимость с прежними payload'ами `/api/ingest` и
  `/api/auth`. При повторном получении ресурса его `raw` обновляется целиком — новые
  подписанные ссылки заменяют устаревшие, при этом статусы уже обработанных файлов
  сохраняются.
- На странице **«Статус загрузки»** можно задать общую папку для фото и видео. Сервер
  проверяет, что каталог создаётся и доступен для записи; выбор сохраняется после
  перезапуска. Смена папки действует на новые загрузки и не переносит старые файлы.
  По умолчанию файлы лежат в пользовательском каталоге данных: Windows —
  `%LOCALAPPDATA%\YandexDLDesktop\files`, macOS —
  `~/Library/Application Support/YandexDLDesktop/files`, Linux —
  `$XDG_DATA_HOME/yandexdl-desktop/files` или `~/.local/share/yandexdl-desktop/files`.
- При запуске, смене каталога и поступлении новых метаданных приложение ищет там
  уже сохранённые файлы по дате и имени и помечает совпадения как `done`, чтобы не
  скачивать их повторно. У ранее сохранённых файлов проверяется наличие и ненулевой
  размер, но не выполняется полная проверка целостности содержимого.
- Перед отметкой `done` для новой загрузки проверяется, что итоговый файл существует
  в выбранной папке и прошёл проверку размера. После успешной проверки он не ставится
  в очередь повторно, даже если позже файл вручную удалить. Фото-загрузка больше не
  останавливается автоматически после 15 последовательных ошибок: остальные файлы
  продолжают обрабатываться.
- Добавлены `app/server_runner.py` (запуск Flask в потоке вместо отдельного терминала)
  и `app/main.py` (окно).

## Запуск

```bash
cd yandexdl-desktop
python3 -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python3 app/main.py
```

ffmpeg по-прежнему нужен отдельно, в PATH (для видео).

## Скачивание остальных файлов (вкладка «Файлы»)

Кроме фото и видео из ленты «Фото», программа качает любые файлы Диска: документы, архивы,
музыку, таблицы и т. д. — с сохранением структуры папок, в `<папка для файлов>/Диск/<путь на Диске>`.

1. **Список файлов.** Лента «Фото» других файлов не содержит, поэтому их список берётся из раздела
   «Файлы» на Диске. Два способа:
   - открыть во вкладке браузера `disk.yandex.ru/client/disk` и заходить в папки, прокручивая каждую
     до конца (Диск подгружает список порциями);
   - нажать **«Обойти все папки»** на вкладке «Файлы» страницы статуса (или «Обойти папки» на тулбаре):
     приложение само откроет все папки по очереди в отдельной вкладке «Обход» и прокрутит их.
     Если Диск попросит войти или пройти проверку, обход остановится — пройди её во вкладке и запусти снова.
     «Обойти заново» — пройти все папки ещё раз (найти новые файлы).
2. **Скачивание.** Кнопка **«Скачать файлы»**. Ссылку на каждый файл сервер запрашивает так же, как для
   видео (`models-v2?m=mpfs/url` с куками и `sk`); при обрыве или просроченной ссылке берёт новую и
   докачивает с места обрыва (до 5 попыток). Размер сверяется с размером на Диске, дата изменения
   файла ставится как на Диске. Недопустимые в Windows символы и имена (`a:b?.txt`, `CON.txt`) заменяются.
3. **Фото и видео из папок** по умолчанию пропускаются — их качают вкладки «Фото» и «Видео».
   Галочка «качать и фото/видео из папок» включает и их (тогда они лягут ещё и в `Диск/…`).
4. **Одна папка вместо всего Диска.** В поле «только папка на Диске» можно указать папку — название
   (`Творчество`), путь (`Творчество/Песни`) или ссылку из адресной строки, открыв папку во вкладке Диска
   (`https://disk.yandex.ru/client/disk/Творчество`). Тогда обход, счётчики и загрузка работают только
   внутри неё и её подпапок. Регистр букв на Диске важен; если папка уже встречалась, регистр
   исправится сам. «Весь Диск» — снять ограничение.

Уже скачанное не качается повторно: при запуске, смене папки и новом списке файлов программа проверяет,
нет ли файла по тому же пути с тем же размером.

Как это устроено: перехват (`app/capture_cdp.py`, для mitmproxy — `capture/addon.py`) смотрит все ответы
`/models*` и HTML страниц Диска и забирает из них ресурсы `/disk/…` (объекты с `path`/`id` и `type`
`file`/`dir` или `meta`) → `POST /api/ingest-files` → таблица `files` в `gallery.db` (галерея и загрузка
фото/видео её не трогают) → загрузчик `FileDownloader` в `server/server.py`.

**Что проверено:** вся цепочка — окно приложения, обход папок с подгрузкой при прокрутке, перехват CDP,
сервер, докачка — прогнана на поддельном Диске с форматом ответов, который описан выше. **На настоящем
Диске не проверялось** (нет доступа из песочницы): если Яндекс отдаёт список папки в другой форме, в логе
не будет строк «перехвачен список папки», а на вкладке «Файлы» — найденных файлов. Тогда нужно посмотреть
в DevTools, какой запрос отдаёт список папки, и поправить `find_disk_resources()`.

## Запуск на сервере без экрана (VPS)

`vps/yandexdl-vps.sh` — для Debian/Ubuntu, от root. Программа работает на виртуальном экране (Xvfb) как
служба systemd; в Яндекс входишь сам через noVNC в браузере; обход и скачивание идут через API программы
(`127.0.0.1:8001`) и не прерываются, если закрыть SSH.

```bash
# с своего компьютера: скопировать папку yandexdl/ на сервер
scp -r yandexdl root@СЕРВЕР:/root/
# на сервере
bash /root/yandexdl/vps/yandexdl-vps.sh install   # пакеты, venv, Qt WebEngine, Xvfb, x11vnc, noVNC, службы
yandexdl vnc                # ссылка https://СЕРВЕР:6080/… и одноразовый пароль; войти в Яндекс во вкладке Диска
yandexdl vnc-off            # после входа: noVNC выключается, пароль стирается, порт закрывается
yandexdl fetch Творчество   # выбрать папку, «качать и фото/видео из папок», обход, скачивание, отчёт
yandexdl status             # ход работы; yandexdl logs — лог программы
```

Файлы ложатся в `/root/yandex/Диск/<папка>` (`--dest` — другая папка). Параметры `fetch`:
`--threads 1` — качать по одному файлу; `--no-crawl` — не обходить папки заново, взять список, собранный
раньше (например, чтобы продолжить после перерыва или скачать одну подпапку: `fetch "Творчество/Проза" --no-crawl`).

**Только часть подпапок.** `yandexdl pick "Папка"` открывает папку, показывает пронумерованный список её
подпапок и спрашивает номера нужных; остальные подпапки и файлы прямо в папке пропускаются (не обходятся и не
качаются), выбранные обходятся. Потом — `yandexdl fetch "Папка" --no-crawl …`.

**Всё, кроме некоторых папок.** `yandexdl fetch / --exclude "Творчество" --exclude "Фото/2019" …` — весь Диск
(`/`; можно и любую папку), кроме указанных подпапок (путь от корня Диска): их не обходят, не считают и не качают,
статусы их файлов не меняются. Папку программа должна была уже видеть, иначе `fetch` остановится и покажет, какие
папки лежат рядом. Исключения действуют, пока выбрана эта папка: `fetch` без `--exclude`, `pick` или поле папки
в окне программы их снимают.

**Повреждённые файлы.** После аварии на Яндекс Диске у многих файлов сервер на битых местах отдаёт пустой
ответ или зависает. Загрузчик файлов сначала качает файл целиком; оборвалось — дочитывает его кусками по 256 КБ
через Range (по 3 сразу): что читается, сохраняется, нечитаемые места остаются нулями, смещения не сдвигаются
(аудио обычно играется с паузами на месте дыр). Правый край каждой дыры уточняется кусками по 32 КБ. Такой файл
отмечается скачанным с заметкой «повреждён: потеряно … байт; дыры: …», а не отдавший ни байта — ошибкой
«не читается». `fetch` кладёт рядом со скачанным `_повреждённые_файлы.txt` со списком тех и других;
`--retry-failed` — ещё раз попробовать то, что не скачалось.

**Если всё на сервер не помещается** — `fetch "Творчество" --rclone gdrive:Яндекс` качает частями: когда
на сервере остаётся меньше 2 ГБ (`--reserve-gb`) или скачано `--part-gb` ГБ, загрузка встаёт на паузу,
скачанное уезжает в облако через `rclone move` (в `gdrive:Яндекс/Творчество/…`, структура папок
сохраняется), и загрузка продолжается. Перенесённое повторно не качается — в базе программы оно уже скачано.
В конце `fetch` сверяет с облаком число файлов и объём (`rclone size`). Облако заранее настраивается
командой `rclone config` (rclone: `curl https://rclone.org/install.sh | bash`). Данные программы
(база, куки, профиль браузера) — в `/var/lib/yandexdl`. Под root Chromium не запускается с песочницей,
поэтому служба ставит `QTWEBENGINE_DISABLE_SANDBOX=1`.

noVNC отдаётся по https с самодельным сертификатом (браузер предупредит один раз); x11vnc слушает только
localhost. Если не хочется открывать порт вовсе — `ssh -L 6080:127.0.0.1:6080 root@СЕРВЕР` и открыть
`https://127.0.0.1:6080/vnc.html`.

**Если после обхода найдено 0 файлов**, `fetch` сам печатает разбор перехваченных ответов Диска
(`yandexdl diagnose`): служба запускает программу с `YDISK_CAPTURE_DUMP=/var/lib/yandexdl/capture-dump`, и
перехват сохраняет туда ответы `/models*` и HTML страниц Диска (sk и connection_id из тел запросов вырезаются).
По разбору видно, где в ответе лежат пути `/disk/…` и какие поля у этих объектов, — под это правится
`find_disk_resources()`.

## Вход по Face ID / Touch ID / Windows Hello / ключу безопасности (WebAuthn)

Яндекс.Диск может просить подтвердить вход через WebAuthn (биометрия или ключ) как
второй фактор. До Qt/PySide6 6.7 QtWebEngine не давал приложению вообще никакой
возможности отреагировать на такой запрос — страница ждала диалог, а показывать
его было некому, поэтому внешне это выглядело как "окно должно появиться, но
ничего не происходит".

Начиная с **6.7** появился сигнал `QWebEnginePage.webAuthUxRequested` — его ловит
`app/webauthn_dialog.py` и рисует свой диалог под каждое состояние запроса:
выбор аккаунта (`SelectAccount`), ввод PIN от внешнего ключа (`CollectPin`), "жду
подтверждения от сенсора/ключа" (`FinishTokenCollection`), ошибку с кнопкой
"Повторить" (`RequestFailed`). Подключается он в `main.py` на каждую обычную
вкладку браузера (не на служебную вкладку с нашим localhost).

**Что этот диалог НЕ делает** — не рисует сам системный Touch ID / Windows Hello
попап с "приложи палец": это всегда показывает ОС, не мы, автоматически, когда
встроенный в Qt Chromium дозванивается до платформенного аутентификатора.
Технически это две разные вещи:

- **Windows Hello** обычно работает "из коробки" у любого современного
  Chromium-движка — Windows сама подсовывает его как платформенного
  аутентификатора любому приложению, которое умеет WebAuthn.
- **Touch ID на macOS** — более капризная история: доступ к Secure Enclave
  Chromium получает только если приложение правильно подписано (code signing) с
  нужными entitlements и Team ID. Это ровно та причина, по которой Electron
  пришлось добавлять отдельный `app.configureWebAuthn()` для своих приложений —
  "просто Chromium внутри" этого не гарантирует. У нас пока обычный dev-запуск
  без подписи, так что на macOS Touch ID может не подняться вообще, даже если
  наш диалог для `SelectAccount`/`CollectPin` отработает нормально. Это не
  проверялось вживую и, скорее всего, всплывёт только на этапе подписи
  macOS-сборки (PyInstaller + `codesign`/notarization).

Если после обновления до 6.7 вход по ключу/PIN заработал, а биометрия
(Face ID/Touch ID) — нет, тестируй сначала на Windows (должно быть проще), а по
macOS разбираться отдельно, когда дойдём до подписи сборки.

## Статус / известные ограничения прототипа

Я написал код по документации CDP и Qt, но **не смог запустить и протестировать его** —
в песочнице нет сети для `pip install PySide6` и нет доступа к реальному Яндекс.Диску.
Прежде чем считать это рабочим, нужно проверить вживую следующие места:

1. **`Network.requestWillBeSentExtraInfo` / `responseReceivedExtraInfo`** — именно они
   должны отдавать «сырой» заголовок `Cookie` и `Set-Cookie` (в обычных
   `Network.requestWillBeSent`/`responseReceived` Chromium их прячет). Нужно проверить,
   что версия Chromium, с которой собран конкретный PySide6, действительно их шлёт —
   по идее да (это давно стабильная часть протокола), но не проверено.
2. **`Network.getResponseBody` сразу после `Network.loadingFinished`** — стандартный
   паттерн, но если тело окажется недоступно (例えば response уже evicted из кэша),
   нужно будет либо раньше вызывать (на `responseReceived`), либо ретраить.
3. **Множественные `Set-Cookie` в одной строке через `\n`** — такое поведение CDP
   документировано, но стоит свериться на реальных ответах Яндекса.
4. **QWebEngineProfile + remote debugging** — `QTWEBENGINE_REMOTE_DEBUGGING` должен
   быть выставлен до первого импорта `QtWebEngine*`, это сделано в начале `main.py`;
   но может понадобиться доп. флаг, если PySide6 использует off-the-record профиль
   по умолчанию для DevTools.
5. **Поиск вкладок — поллингом раз в 2 секунды** (`http://127.0.0.1:<port>/json`), не
   событиями. Для прототипа этого достаточно (открытие новой вкладки с Диском будет
   подхвачено с задержкой до ~2 сек), но при желании можно заменить на push через
   CDP `Target.setDiscoverTargets` — будет мгновенно, но потребует отдельного
   browser-level websocket-соединения и больше кода.
6. `site_view` (закреплённая вкладка 0) создаётся на дефолтном/off-the-record профиле
   Qt, а не на `self.browser_profile` — это нормально, т.к. она ходит только на свой
   localhost и ей не нужны куки Яндекса; но если понадобится что-то специфичное для
   неё — профиль можно сменить так же, как у обычных вкладок.

## Чего пока нет (следующие шаги)

- Упаковка в один бинарник на каждую ОС (PyInstaller/Nuitka) — пока только `pip install` + `python app/main.py`.
- Бандлинг ffmpeg под каждую ОС.
- Обработка случая, когда вкладка с Диском перезагружается/закрывается (переподключение частично есть — `_run()` в `capture_cdp.py` ретраит поиск таргета, но сама сессия захвата при обрыве сокета стартует заново без потери прогресса в `server.py`, т.к. вся прогрессия хранится в SQLite).
- Кнопки «открыть Диск заново» / индикатор «авторизация жива» в UI (сейчас это видно только по логу и по `/status` во встроенной вкладке).
- Иконки вкладок (favicon), история вкладок, горячие клавиши (Ctrl+T/Ctrl+W/Ctrl+L) — пока не делал, браузер максимально простой.

Короче: архитектурно это должно работать и явно проще в использовании, чем связка
mitmproxy + системный прокси + сертификат, но первый реальный прогон обязательно
вскроет мелочи в CDP-части — он не отлаживался на живом трафике.
